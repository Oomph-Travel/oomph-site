# /links/ LCP — 2026-07-28

Follow-up to the open item from the 2026-07-27 session: production `/links/`
medians 3.19s LCP (5 runs: 2.94 / 3.01 / 3.19 / 6.73 / 6.73) against the 2.5s
bar. Re-measured today with `npx lighthouse` (mobile default) from a
residential connection: 2.8 / 6.7 / 6.7 / 6.8 — same bimodal shape
[`2026-07-25-lcp-workstream.md`](2026-07-25-lcp-workstream.md) documents.

**Verdict: there is no theme-side fix. The gap is the SG Optimizer combined
stylesheet being render-blocking, and the lever is the dashboard critical-CSS
pass already recommended in the 2026-07-25 audit. `/links/` is not special —
it inherits the sitewide residual.**

## Where the time goes (fast-mode run, 2.8s)

LCP element is the featured-card image (`.oomph-links__feature-img`).

| Phase | ms | What it is |
|---|---|---|
| TTFB | 635 | Almost entirely Lighthouse's simulated mobile RTT — the real server response is ~50ms (`server-response-time` audit). Not addressable. |
| Load Delay | 1,064 | The image request queues behind the 186KB render-blocking combined CSS under simulated bandwidth contention. |
| Load Time | 717 | 64KB JPEG over the simulated connection. |
| Render Delay | 348 | Waiting for the combined CSS to finish before first paint. (4,000ms+ in slow-mode runs — this phase is what the bimodality inflates.) |

Load Delay and Render Delay — the two biggest addressable phases — are both
the combined stylesheet. Critical-CSS delivery would collapse them and bring
even a conservative estimate well under the bar.

## Why the theme has no move left

- The image markup already does everything R3 asks: `loading="eager"`,
  `fetchpriority="high"`, explicit `width`/`height`, srcset. Lighthouse's
  `prioritize-lcp-image` audit **passes**.
- A `<head>` preload would not help: the `<img>` sits in the first 77KB of
  HTML and is discovered by the preload scanner immediately; the delay is
  bandwidth contention, not discovery, and `fetchpriority="high"` is already
  set.
- The srcset choice is nearly optimal: the card maxes at 34rem, the browser
  downloads the 768w/64KB variant, and `uses-responsive-images` finds only
  ~15KB of savings. Tightening `sizes` doesn't change the selected candidate
  at mobile DPR.
- The featured image is a **Media Library** image that auto-follows the newest
  Journal post, so `npm run images` (theme-asset WebP variants) can never
  cover it. WebP here means SG Optimizer's Media WebP generation — a
  dashboard toggle, not code.

## The dashboard fix does not exist — correcting Finding #9

The standing recommendation since the 2026-07-21 audit was "turn on SG
Optimizer's critical-CSS/deferred-CSS options." **Speed Optimizer has no such
option.** Verified against the live plugin UI on staging2 (v7.x, Frontend →
CSS), which offers exactly five controls:

| Control | State |
|---|---|
| Minify CSS Files | on |
| Exclude from CSS Minification | — |
| Combine CSS Files | on |
| Exclude from CSS Combination | — |
| Preload Combined CSS | on |

All three toggles are already enabled. That is the whole CSS surface of the
plugin; critical CSS has been an open SiteGround feature request for years and
has never shipped. Finding #9 recommended a control that was never there, and
the 2026-07-25 doc repeated it without checking. **There is no CSS setting
left to enable.**

**Enabled and verified 2026-07-28: Media → WebP.** The featured image now
serves at 42KB against 64KB for the JPEG (−34%), the 300px variant at 8KB
against 12KB, with JPEG fallback intact for non-supporting clients. Measurable
but small — image download was never the binding constraint. LCP after: 6.8 /
2.8 / 7.7s, statistically unchanged.

## What the 182KB stylesheet is actually made of

Rule-bytes by owner, from the live combined file:

| Owner | Bytes | Share |
|---|---|---|
| Kadence parent + WP core + misc | 91.0 KB | 48.8% |
| **Fluent Forms** | **42.9 KB** | **23.0%** |
| `.oomph-*` (this theme) | 22.8 KB | 12.3% |
| `.wp-block-*` | 12.8 KB | 6.9% |
| Kadence blocks (`.kb-`/`.kt-`) | 14.5 KB | 7.8% |

Fluent Forms is the single largest identifiable block, and it loads on
`/links/` — legitimately: the sitewide footer carries the newsletter subscribe
form (form ID 4). 43KB of CSS for one email field is a poor trade, but
dequeuing it is not a one-liner; it would mean either dropping the footer form
from lean pages or serving a minimal hand-written style for it. That is a real
decision about the newsletter capture surface, not a performance tweak.

## Honest assessment of the remaining gap

Fast-mode render delay is already only ~350ms. Eliminating render-blocking CSS
entirely would take a 2.8s fast-mode run to roughly 2.4s — at the bar, not
comfortably past it — and would do nothing about the ~6.7s slow mode, which
[`2026-07-25-lcp-workstream.md`](2026-07-25-lcp-workstream.md) established is
a network-path artifact of Lighthouse's simulated throttling, not page weight.

So: **the lab number may never reliably read under 2.5s, and chasing it
further has poor expected value.** The remaining levers, in descending
order of payoff per unit of risk:

1. **Check CrUX field data** (Search Console → Core Web Vitals, or
   pagespeed.web.dev) — real visitors on real connections. This is the number
   Google ranks on and the only one that settles the question. Free, and it
   should be the next step before any further work.
2. **Reconsider the footer newsletter form's cost** (43KB CSS sitewide) — a
   product decision, R64-adjacent, needs Eric.
3. **Hand-rolled critical CSS in the child theme** — inline above-the-fold
   rules, load the rest async. Technically possible, fights SG Optimizer's
   combination step, and risks the flash-of-unstyled-content it is meant to
   prevent. Not recommended without field data first showing a real problem.
