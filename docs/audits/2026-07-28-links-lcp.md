# /links/ LCP — 2026-07-28

Follow-up to the open item from the 2026-07-27 session: production `/links/`
medians 3.19s LCP (5 runs: 2.94 / 3.01 / 3.19 / 6.73 / 6.73) against the 2.5s
bar. Re-measured today with `npx lighthouse` (mobile default) from a
residential connection: 2.8 / 6.7 / 6.7 / 6.8 — same bimodal shape
[`2026-07-25-lcp-workstream.md`](2026-07-25-lcp-workstream.md) documents.

**Verdict: there is no theme-side fix. The gap is the SG Optimizer combined
stylesheet being render-blocking, and the lever is the dashboard critical-CSS
pass already recommended in the 2026-07-25 audit. `/links/` is not special —
it inherits the sitewide residual.**

## Where the time goes (fast-mode run, 2.8s)

LCP element is the featured-card image (`.oomph-links__feature-img`).

| Phase | ms | What it is |
|---|---|---|
| TTFB | 635 | Almost entirely Lighthouse's simulated mobile RTT — the real server response is ~50ms (`server-response-time` audit). Not addressable. |
| Load Delay | 1,064 | The image request queues behind the 186KB render-blocking combined CSS under simulated bandwidth contention. |
| Load Time | 717 | 64KB JPEG over the simulated connection. |
| Render Delay | 348 | Waiting for the combined CSS to finish before first paint. (4,000ms+ in slow-mode runs — this phase is what the bimodality inflates.) |

Load Delay and Render Delay — the two biggest addressable phases — are both
the combined stylesheet. Critical-CSS delivery would collapse them and bring
even a conservative estimate well under the bar.

## Why the theme has no move left

- The image markup already does everything R3 asks: `loading="eager"`,
  `fetchpriority="high"`, explicit `width`/`height`, srcset. Lighthouse's
  `prioritize-lcp-image` audit **passes**.
- A `<head>` preload would not help: the `<img>` sits in the first 77KB of
  HTML and is discovered by the preload scanner immediately; the delay is
  bandwidth contention, not discovery, and `fetchpriority="high"` is already
  set.
- The srcset choice is nearly optimal: the card maxes at 34rem, the browser
  downloads the 768w/64KB variant, and `uses-responsive-images` finds only
  ~15KB of savings. Tightening `sizes` doesn't change the selected candidate
  at mobile DPR.
- The featured image is a **Media Library** image that auto-follows the newest
  Journal post, so `npm run images` (theme-asset WebP variants) can never
  cover it. WebP here means SG Optimizer's Media WebP generation — a
  dashboard toggle, not code.

## Actions (both dashboard, both Eric, both staging-first)

1. **SG Optimizer → Frontend → CSS: enable "Optimize CSS delivery"
   (critical CSS)** — the standing recommendation from Finding #9 /
   2026-07-25. This is the fix; it moves every page, not just `/links/`.
   Critical-CSS generation can break rendering, so validate on staging2 and
   eyeball the deep-ground pages (`/links/`, cruise singles) specifically.
2. **SG Optimizer → Media: enable WebP generation** — turns this 64KB JPEG
   into ~40KB for free and covers every future featured image. Secondary;
   worth flipping while in the dashboard.

Lab numbers can't fully settle this — after the settings change, check CrUX
p75 (Search Console → Core Web Vitals) over the following 28 days.
